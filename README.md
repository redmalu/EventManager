## Event Manager API
RESTful Web API Сервис для управления мероприятиями (событиями).  Позволяет создавать, просматривать, обновлять и удалять информацию о событиях.  
Реализовано на ASP.NET Core с хранением данных в памяти

## Возможности
- Полный CRUD (Create, Read, Update, Delete) для управления событиями.
- Создание бронирования для события
- Архитектура, разделенная на слои (Presentation, Application, Models).
- Интеграция **Swagger/OpenAPI** для интерактивной документации.
- Централизованная обработка ошибок с поддержкой стандарта **Problem Details** (RFC 7807).
- Настроенный **CORS** для взаимодействия с любыми фронтенд-приложениями.
- Внедрение зависимостей (Dependency Injection) и логирование.

## Стек технологий
- **Язык**: C# 12+
- **Фреймворк**: ASP.NET Core Web API .NET 10
- **Документация**: Swagger / OpenAPI
- **Хранение данных**: In-Memory (список в памяти, для демонстрации/прототипа)
- **Архитектура**: Слоистая архитектура (Layered Architecture)

## API Endpoints
Events
 - GET '/api/events'- Получить отфильтрованный и пагинированный список всех событий.
	- title string Фильтр по названию (case-insensitive, частичное совпадение)
	- from datetime События, начинающиеся не ранее указанной даты
	- to datetime События, заканчивающиеся не позднее указанной даты
	- page int Номер страницы (≥ 1) - по умолчанию 1
	- pageSize int Размер страницы (от 5 до 100) по умолчанию 10
 - GET '/api/events/{id}' - Получить событие по ID. 
 - POST '/api/events' - Создать новое событие.
 - PUT '/api/events/{id}' - Обновить существующее событие.
 - DELETE '/api/events/{id}' - Удалить событие по ID.

 Bookings
 - POST 'api/events/{id}/book' - создание бронирования для события
 - GET 'api/bookings/{id}' - получение детальной информации о конкретной брони по её идентификатору


## 📦 Модель Booking и статусы

Сущность `Booking` представляет собой заявку пользователя на участие в мероприятии. 

### Структура модели
| Поле | Тип | Описание |
| :--- | :--- | :--- |
| `Id` | `Guid` | Уникальный идентификатор бронирования. |
| `EventId` | `Guid` | Идентификатор события, на которое создается бронь. |
| `Status` | `BookingStatus` | Текущий статус бронирования (см. ниже). |
| `CreatedAt` | `DateTime` | Дата и время создания заявки (в UTC). |
| `ProcessedAt` | `DateTime?` | Дата и время обработки заявки фоновым сервисом (null, если статус `Pending`). |

### Статусы бронирования (`BookingStatus`)
Жизненный цикл бронирования управляется через следующие статусы:
1. **`Pending` (Ожидает)** — начальный статус. Бронь создана, но еще не обработана системой.
2. **`Confirmed` (Подтверждена)** — бронь успешно обработана фоновым сервисом, место зарезервировано.
3. **`Rejected` (Отклонена)** — бронь отклонена (вручную администратором или из-за нехватки мест/ошибок валидации).

### Пример запроса (POST /api/events)
**Request Body:**
```json
{
  "title": "Конференция по .NET",
  "description": "Ежегодная встреча разработчиков",
  "startAt": "2024-11-15T10:00:00Z",
  "endAt": "2024-11-15T18:00:00Z"
}
```
**Response (201 Created):**
```json
{
  "id": "aaa...111",
  "title": "Конференция по .NET",
  "description": "Ежегодная встреча разработчиков",
  "startAt": "2024-11-15T10:00:00Z",
  "endAt": "2024-11-15T18:00:00Z"
}
```

## ⚙️ Логика фоновой обработки (`BookingProcessor`)

Обработка бронирований вынесена в фоновый сервис (`BackgroundService`), чтобы не блокировать HTTP-запросы и обеспечить асинхронную обработку очередей.

**Алгоритм работы:**
1. Сервис работает в бесконечном цикле, пока приложение не получит сигнал на остановку (`stoppingToken`).
2. Создает новую область зависимостей (`IServiceScope`) для корректной работы с scoped-сервисами (например, репозиторием).
3. Запрашивает из репозитория все бронирования и фильтрует только те, у которых `Status == BookingStatus.Pending`.
4. Для каждого найденного бронирования:
   - Имитирует время обработки (в демо-режиме: `Task.Delay(2s)`).
   - Меняет статус на `Confirmed`.
   - Устанавливает `ProcessedAt = DateTime.UtcNow`.
   - Сохраняет изменения в репозиторий.
5. Блок `try-catch` гарантирует, что ошибка при обработке одной брони не остановит обработку остальных в текущем цикле.
6. После обработки всей партии сервис "засыпает" на 20 секунд перед следующей итерацией опроса.

## Пример сценария использования (Use Case)

Ниже приведен типичный сценарий взаимодействия клиента с системой бронирования.

**Шаг 1: Создание события**  
Клиент создает новое событие и получает его `eventId`.
```http
POST /api/events
{ "title": "Концерт рок-группы", "startAt": "2024-12-01T19:00:00Z", "endAt": "2024-12-01T22:00:00Z" }
// Ответ: 201 Created, { "id": "aaa...111", ... }
```

**Шаг 2: Создание бронирования**  
Пользователь решает забронировать место на это событие.
```http
POST /api/events/aaa...111/book
// Ответ: 202 Accepted
{
  "id": "bbb...222",
  "eventId": "aaa...111",
  "status": "Pending"
}
```

**Шаг 3: Проверка статуса сразу после создания**  
Пользователь проверяет статус своей заявки.
```http
GET /api/bookings/bbb...222
// Ответ: 200 OK
{
  "id": "bbb...222",
  "eventId": "aaa...111",
  "status": "Pending",
  "createdAt": "2024-10-25T12:00:00Z",
  "processedAt": null
}
```

**Шаг 4: Ожидание фоновой обработки**  
Проходит ~20 секунд. Фоновый сервис `BookingProcessor` находит эту заявку, обрабатывает её и обновляет в базе данных.

**Шаг 5: Финальная проверка статуса**  
Пользователь снова запрашивает информацию о бронировании.
```http
GET /api/bookings/bbb...222
// Ответ: 200 OK
{
  "id": "bbb...222",
  "eventId": "aaa...111",
  "status": "Confirmed",
  "createdAt": "2024-10-25T12:00:00Z",
  "processedAt": "2024-10-25T12:00:22Z" 
}
```
*Бронирование успешно подтверждено, поле `processedAt` заполнено.*

# Запуск тестов

Проект содержит модульные тесты, написанные с использованием **xUnit** и **Moq**.

## Требования

- [.NET SDK 8.0+](https://dotnet.microsoft.com/download)
- Перейдите в папку с тестовым проектом (например, `TestEventManager`)

## Запуск всех тестов

```bash
dotnet test
```

## Запуск с подробным выводом

```bash
dotnet test --verbosity normal
```

Уровни детализации: `quiet`, `minimal`, `normal`, `detailed`, `diagnostic`.

## Фильтрация тестов

Тесты помечены трейтом `[Trait("Category", "...")]`. Это позволяет запускать только нужные группы:

```bash
# Только тесты удаления
dotnet test --filter "Category=DeleteEvent"

# Только тесты обновления
dotnet test --filter "Category=UpdateEvent"

# Объединение нескольких категорий (логическое ИЛИ)
dotnet test --filter "Category=DeleteEvent|Category=UpdateEvent"

# Полнотекстовый поиск по имени теста
dotnet test --filter "FullyQualifiedName~TryDeleteEvent"
```
